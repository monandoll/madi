# CoreText 자막 재현 — 실측 기록 (2026-09-25)

0단계 통과 조건 A. `docs/stage-0.spec.md`.

렌더러를 Remotion(CSS) 에서 CoreText 로 바꿨으므로 값을 다시 잡았다.
목표 숫자(`AGENTS.md §9`)는 렌더러와 무관한 사실이라 그대로 쓰고, 그 숫자를 내는
스타일 값만 새로 구했다.

- 골든 프레임: `reference/yt_15s.png` (720x1280). `tools/measure.mjs` 의 세 목표치를
  전부 통과하는 유일한 프레임이라 기준으로 썼다
- 교차 확인: `reference/yt_11s.png`, `reference/yt_7s.png`
- 결과 값: `Madi/Resources/styles/short.v1.json`

## 1. 결론부터 — 원본은 "stroke 밑에 fill" 로 그려졌다

`docs/stage-0.spec.md` 의 알려진 함정은 `strokeWidth` 를 **음수**로 주라고 적었다.
음수면 CoreText 가 fill → stroke 순으로 그려서 **획 절반이 글자 안쪽을 파먹는다.**
원본은 그렇지 않다.

`yt_15s.png` 세로 스캔 (x=155):

```
  y=929..932   검정 (0,0,0)       4px
  y=933..978   흰색 (255,255,255) 46px
  y=979..983   검정                5px
```

검은 띠 바로 다음이 **온전한 흰색**이다. 외곽선이 중앙 기준으로 그려졌다면
검정이 글자 경계 안쪽으로 4px 더 들어와 흰색이 y=937 부터 시작해야 한다. 아니었다.

→ `CaptionLayer` 는 **두 번 그린다**: 양수 `strokeWidth` 로 외곽선만 깔고, 그 위에 fill.
  이러면 글자 높이 = 잉크 높이가 되어 목표치 역산이 단순해진다.

## 2. 글자 높이 ÷ 폰트 크기 = 0.9023

Remotion(CSS) 에서는 0.889 였다. CoreText 는 다르므로 다시 쟀다.

`CTLineGetBoundsWithOptions(.useGlyphPathBounds)` 로 기준 문자열 `"가힣"` 을 size 1000 에서
재서 나눈 값이다. **폰트나 웨이트를 바꾸면 이 값도 바뀐다.** 그래서 상수로 적지 않고
`CaptionLayout.metrics()` 가 매번 역산한다. `short.v1.json` 에 포인트 크기는 없다.

기준 문자열이 실제 자막과 같은 높이를 내는지 확인했다 (1080x1920, wght 480):

| 문자열 | 잉크 높이 |
|---|---|
| 가힣 (기준) | 68.93 |
| 가능성이 높다는 겁니다 | 68.70 |
| 어깨가 | 68.74 |
| 골반 틀어졌으면 | 68.70 |
| 하나 둘 셋 | 68.48 |

최대 0.45px 차이. **원본이 "크기 고정, fit-to-width 아님" 이라는 판정과 일치한다.**

## 3. 웨이트 480 — 눈이 틀렸고 픽셀이 맞았다

처음에 800(ExtraBold)으로 뒀다. 근거는 없었다. archive 의 Remotion 토큰이 `fontWeight: 800`
이었고 그걸 그대로 옮겼을 뿐이다. **전작이 디자인 시안 색을 그대로 박은 것과 같은 실수다.**

### 픽셀은 처음부터 450~550 이라고 했다

흰 픽셀(`>230`) 개수로 센 "세로획 ÷ 글자 높이":

| | 비율 |
|---|---|
| 원본 yt_15s | 0.0870~0.1087 (세로획 4~5px / 글자 높이 46px) |
| 내 렌더 wght 500 | 0.1087 |
| 내 렌더 wght 800 | 0.1760 |

800 은 원본의 1.6배였다. 그런데 3배 확대해서 나란히 보니 원본이 500 보다 굵어 보여서
측정을 믿지 않았다. **그게 틀렸다.** 6배로 다시 키우니 550 부터 `ㅇ` 카운터가 확연히
작아지고, 원본은 450~500 사이였다. 3배에서는 외곽선 두께에 속았다.

### 측정을 보강해서 확정했다

흰 픽셀 개수는 원본에 불리하다. 유튜브 720p 재인코딩본이라 검은 외곽선이 흰 획으로
번져서 경계 픽셀이 임계값 아래로 떨어진다. 원본 한 행의 생값:

```
x=135:0  136:224  137:255 ... 141:255  142:84  143:0
```

`>230` 으로 세면 5px, **루마 50% 교차**로 재면 6.17px. 1.2px 가 번짐에 먹혔다.
crisp 한 내 렌더는 0.3px 밖에 안 먹히므로, 개수로 비교하면 내 쪽이 늘 굵게 나온다.

→ `StillRenderer.scanStrokes` 를 50% 교차 방식으로 바꿨다 (`madi-spike stems`).
  원본과 내 렌더를 **같은 코드**로 잰다.

| | 원본 | wght 480 |
|---|---|---|
| yt_15s | 0.1155 | 0.1180 |
| yt_11s | 0.1187 | — |

### 결정적 교차 검증 — 잉크 폭

웨이트만 맞추면 우연일 수 있다. 서로 다른 두 자막의 **폭**이 동시에 맞는지 봤다:

| 자막 | 원본 폭 | wght 480 |
|---|---|---|
| 가능성이 높다는 겁니다 | 473px | 474px |
| 양 쪽을 비교해봤을때, | 438px | 437px |

1px 안에서 맞는다. **원본 폰트가 Pretendard 이거나 메트릭이 같다**는 뜻이다.
wght 800 일 때는 462px 로 11px 좁았다.

"눈으로 보고 값을 고치지 않는다" 는 규칙이 또 한 번 맞았다.

## 4. 보조 문구 — archive 토큰 두 개가 틀렸다

6배 확대해서 확인한 것:

| 항목 | archive/remotion 토큰 | 실측 |
|---|---|---|
| 이탤릭 | `italic: true` | **아니다.** 글자가 곧게 서 있다 |
| 외곽선 | `strokeWidth: 5` | **없다.** 흐린 그림자만 있다 |
| 색 | `#FFE04D` | `#FEE374` (스포이드) |

크기와 위치:

- 라틴 어센더 높이 16px @1280 (= 24px @1920) → `scale` 0.4444, `weight` 400
- 그 값에서 잉크 폭이 원본과 **정확히 같다** (195px, yt_15s)
- 베이스라인: 행별 노란 픽셀 수가 뚝 끊기는 행. yt_15s 와 yt_7s **둘 다 y=1020 @1280**
  → `baselineBottomRatio` = (1280-1020-1)/1280 = **0.2023**

### 본문은 잉크 아래끝, 보조는 베이스라인으로 잡는다

라틴은 `y` · `g` 의 디센더 유무가 문구마다 달라서 잉크 아래끝이 흔들린다.
한글 본문은 안 흔들리므로 잉크 아래끝(= `measure.mjs` 가 재는 값)으로 잡는 게 낫다.

## 5. 그림자 — 있다. 신뢰도 낮음

글자 **위쪽** 검은 띠는 배경으로 딱 끊기는데 **아래쪽**은 번진다:

```
위:  928:배경(114)  929:16  930..932:0      → 경계가 1px
아래: 979:19  980..982:0  983:8  984:35  985:64  986:배경(81)  → 경계가 3px
```

아래로 내린 흐린 그림자다. 보조 문구(외곽선이 없는데도 오른쪽 아래가 어둡다)에서 더 뚜렷하다.

⚠ 유튜브 재인코딩 번짐과 구분이 어렵다. `shadow.enabled` 를 false 로 두면 외곽선만 그린다.
인스타 원본이 들어오면 다시 본다.

## 6-1. 보조 지표를 "아래끝" 에서 "베이스라인" 으로 바꿨다

처음 측정에서 보조 문구가 0.1984 로 목표 0.204 에 0.0056 못 미쳤다.
**위치 문제가 아니라 측정 정의 문제였다.**

`measure.mjs` 의 "보조하단" 은 **노란 픽셀이 찍힌 가장 아래 행**이었다.
crisp 한 렌더에서는 그게 `y` · `g` 의 디센더 끝이고, 흐린 원본에서는 디센더가
임계값 아래로 사라져서 베이스라인 근처가 잡힌다. 같은 자리를 재는 값이 아니다.

글자를 한 픽셀도 안 움직이고 문구만 바꿔 보면 바로 드러난다:

| 보조 문구 | 아래끝 기준 | |
|---|---|---|
| `is likely misaligned.` (y·g 있음) | 0.1984 | FAIL |
| `is likely misaligned` (y·g 있음) | 0.1984 | FAIL |
| `COMPARE BOTH SIDES` (디센더 없음) | 0.2021 | PASS |

→ 지표를 **베이스라인**(행별 픽셀 수가 뚝 떨어지는 행)으로 바꿨다.
  디센더 유무와 무관하고, 재인코딩 번짐에도 흔들리지 않는다.

바꾸고 나니 원본 4장에서 값이 거의 한 점으로 모인다:

| 프레임 | 베이스라인 | (참고) 아래끝 |
|---|---|---|
| yt_15s | 0.2023 | 0.2000 |
| yt_7s | 0.2023 | 0.2016 |
| yt_13s | 0.2023 | 0.2008 |
| yt_11s | 0.2000 | 0.1867 |
| **내 렌더** | **0.2021** | 0.1984 |

아래끝은 0.1867~0.2016 으로 0.015 나 흔들리는데 베이스라인은 0.0023 안에 들어온다.
**새 목표치 0.2023 은 이 4장에서 나온 값이다.**

덤으로 `yt_11s` 가 예전 지표에서는 FAIL 이었는데 이제 PASS 한다 — 원본이 목표를
통과하지 못하던 것은 원본이 이상해서가 아니라 자가 이상했던 것이다.

## 7. 남은 것

- `caption.lineGapRatio` **미측정.** `reference/` 34장에 2줄 자막 프레임이 없다.
  지금 값 1.35 는 근거가 없다. 2줄 자막 프레임을 확보하면 잰다
- `popInSec` · `popInScaleFrom` **미측정.** 연속 프레임이 필요하다
- `maxWidthRatio` 0.90 은 clamp 라 실측 대상이 아니다 (11자가 폭의 0.657 을 쓴다)
- `reframe.*` 는 1단계 값이다. 0단계에서 읽지 않는다
- yt_15s 의 보조 문구가 화면 중앙에서 5px 왼쪽에 있다. yt_7s 는 1.5px 라
  **일관되지 않아서 보정하지 않았다.** 1편 보고 정하지 않는다 (`AGENTS.md §0-7`)
- `short.v1.json` 의 `measured` 는 여전히 `false`. 자막 치수는 아직 유튜브 숏츠에서만 쟀다.
  인스타 릴스 원본이 들어오면 5편으로 다시 잰다 (`docs/style-authoring.md §1`)

## 8. 통과 조건 B — 영상 한 편

`spike/composition.json` → `out/spike.mp4`. 18.50초 · 1080x1920 · 30fps · 장면 3개 · 자막 15개.

원본은 크리에이터 공개 숏츠(`EDpBGkaNJmU`)를 yt-dlp 로 받은 **1080x1920 · 59.95fps · H.264** 다.
`reference/` 프레임 34장은 브라우저에서 720x1280 으로 캡처한 것이라, 이번에 처음으로
**네이티브 해상도 원본**과 대조했다.

### 이 영상으로 판정할 수 없는 것

1. **완성본이다.** 자막이 이미 번인돼 있다. 그래서 B 를 "원본을 배경으로 깔고 우리 자막을
   같은 시각·같은 자리에 얹어 포개지는가" 로 판정했다. 어긋나면 자막이 둘로 보인다.
2. **이미 9:16 으로 크롭돼 있다.** 리프레이밍을 검증할 수 없다 → **B-2(구도)는 보류**다.
   촬영 원본(`raw.mp4`)이 들어와야 판정할 수 있다.
3. **유튜브 재인코딩본이다.** 우리 렌더가 더 선명하게 나오는데, 그건 렌더 차이가 아니라
   원본이 압축으로 뭉갠 것이다. 아래에서 이 둘을 구분해 적었다.

### 자막 위치 — 네이티브 원본과 같은 값이 나온다

같은 시각(15.0초) 프레임을 `tools/measure.mjs` 로 잰 것:

| | 본문 높이 | 본문 아래끝 | 보조 베이스라인 |
|---|---|---|---|
| 원본 (네이티브 1080p) | 3.54% | 0.2354 | 0.2026 |
| **우리 렌더** | **3.54%** | **0.2354** | **0.2026** |
| (참고) 원본 720p 캡처 | 3.59% | 0.2352 | 0.2023 |

세 항목이 네이티브 원본과 **자릿수까지 같다.**
720p 캡처와의 0.05%p 차이는 다운스케일 아티팩트였지 우리 렌더 문제가 아니었다.

### 전환 시각 — 15개 경계 전부 포개진다

자막 전환 시점을 0.1초 단위로 좁혀 컴포지션에 적었다
(0.5초 간격 프레임으로 구간을 찾고, 경계마다 0.1초 프레임 4장을 더 떠서 확정).

검증은 **흰 픽셀 수**로 했다. 우리 자막이 원본 자막 위에 정확히 포개지면 흰 픽셀이 거의
그대로지만, 시각이 어긋나면 서로 다른 자막이 동시에 보여 픽셀이 크게 는다.

경계 15곳 × 0.1초 간격 4장 = **60개 시각 전부에서 증가율 0.99~1.03**. 자막 없는 구간
(8.2~10.5초)에서만 배경 노이즈 때문에 절대값이 조금 다른데, 프레임을 열어 보니 둘 다
자막이 없고 흰 양말 가장자리 선명도 차이였다.

### 판정

| # | 항목 | 판정 | 근거 |
|---|---|---|---|
| 1 | 자막 | **통과** | 크기·위치·굵기·외곽선·줄바꿈이 네이티브 원본과 같은 값. 2배 확대에서 구분 불가 |
| 2 | 구도 | **보류 — 촬영 원본 필요** | 소스가 이미 9:16 크롭본이라 리프레이밍을 검증할 수 없다 |
| 3 | 리듬 | **통과** | 자막 전환 60개 시각 전부 포개짐. 장면 3개 컷 지점에서 끊김·중복 프레임 없음 |
| 4 | 훅 | **통과 (제한적)** | 0~1.5초 자막이 원본과 동일하게 뜬다. 다만 훅을 **구성**한 게 아니라 원본 구성을 그대로 옮긴 것이라, 훅 설계는 이 영상으로 검증되지 않는다 |
| 5 | 종합 | **통과** | 전체 프레임을 나란히 놓고 구분되지 않는다 (`frames/2026-09-25-B-compare-full.png`) |

**B-2 를 제외한 4개 통과.** B-2 는 촬영 원본이 들어오면 판정한다.

### 렌더 차이 vs 재인코딩 차이

| 관찰 | 어느 쪽 문제인가 |
|---|---|
| 우리 글자가 더 선명하고 가장자리가 깨끗하다 | **재인코딩.** 원본은 유튜브 H.264 로 뭉개졌다 |
| 자막 없는 구간에서 흰 양말 가장자리 픽셀 수가 다르다 | **재인코딩.** 자막과 무관 |
| 보조 문구가 살짝 두꺼워 보이는 프레임이 있다 | **우리 것 위에 원본 것이 겹친 것.** 원본 보조 문구의 가로 중심이 프레임마다 1.5~5px 흔들려서 완전히 겹치지 않는다. 본문은 흔들리지 않는다 |
| 60fps → 30fps | **설정.** `Composition.fps` 가 30 이다. 원본은 59.95fps |

## 9. 자막 한 줄 최대 글자 수가 틀렸다 — 13자 → 15자

`AGENTS.md §9` 는 "한 줄 최대 **12자**", 품질 게이트 **G5** 는 "한 덩어리 **13자** 이내" 다.
전편 18.5초에서 자막 15개를 다 읽어 보니 **15자짜리가 한 줄로 나온다.**

| 자막 | 글자 수 | 원본 |
|---|---|---|
| 반대쪽도 똑같이 진행해주세요 | **15** | 한 줄 |
| 다음 영상으로 해결해보세요 | **14** | 한 줄 |
| 골반이 틀어지신 분들은 | 12 | 한 줄 |
| 양 쪽을 비교해봤을때, | 12 | 한 줄 |

`maxChars: 13` 으로 렌더했더니 15자 자막이 **두 줄로 쪼개져** 원본과 달라졌다.
15 로 올리니 한 줄로 나오고 폭도 0.844 로 상한(0.90) 안에 들어온다.

> 실제로 글자 수는 제약이 아니다. **폭이 제약이다.** `maxWidthRatio` 가 이미 그걸 막는다.
> `maxChars` 는 근사치일 뿐인데, 그 근사치가 크리에이터 실제 자막을 통과시키지 못했다.

**G4 를 4.5% 로 뒀다가 크리에이터 영상이 통과 못 한 것과 같은 종류의 오류다**
(`docs/findings/2026-09-23-reference-measurement.md §4`).
`short.v1.json` 의 `maxChars` 는 15 로 고쳤다. **`AGENTS.md §9` 의 "12자" 와 `§8 G5` 의
"13자" 는 아직 그대로다** — 사람이 정할 일이라 건드리지 않았다.
